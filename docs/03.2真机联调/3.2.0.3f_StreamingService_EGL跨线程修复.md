# MVP-2 批次 3.2.0.3f 真机联调记录

> 设备: Oplus PLC110 (ColorOS 14, Android 14) + Windows 11 PC
> 日期: 2026-06-09
> 目标: 修复 Oplus Hans 冻结子线程 + 修复 EGL 跨线程静默失败

## 背景

3.2.0.3e 批次真机联调时发现 Oplus ColorOS 的 Hans 应用冻结管理器
会冻结非前台应用的子线程。原批次 3.2.0.3b 在 `Streaming-Start-Thread`
子线程跑 startStreaming 逻辑, 推流卡住不动。

3.2.0.3e 曾尝试 "改回点按钮" (物理点击主线程), 但无法根本解决 Hans 冻结。

## 3.2.0.3f 方案

### 1. 创建前台 Service (StreamingService)

把 startStreaming 6 步逻辑从 MainActivity 迁入 `StreamingService.onStartCommand`,
通过 `startForeground(NOTIF_ID, ...)` 标记 Service 为前台任务, 避免 Hans 冻结。

```kotlin
class StreamingService : Service() {
    // 推流资源 (companion object 静态, MainActivity listener 跨 Service 边界读)
    @Volatile var sActive: Boolean = false
    @Volatile var sH264Encoder: H264Encoder? = null
    @Volatile var sEglRenderer: EglRenderer? = null
    @Volatile var sTcpServer: TcpStreamServer? = null
}
```

### 2. AndroidManifest 权限 + Service 注册

```xml
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_CAMERA" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

<service
    android:name=".StreamingService"
    android:exported="false"
    android:foregroundServiceType="camera" />
```

### 3. TcpStreamServer SO_REUSEADDR

旧 `ServerSocket(port)` 构造不暴露 SO_REUSEADDR, 99 99 端口被 adb reverse
占用时重启会卡 60s TIME_WAIT。改用:
```kotlin
serverSocket = java.net.ServerSocket()
serverSocket!!.reuseAddress = true
serverSocket!!.bind(java.net.InetSocketAddress("0.0.0.0", port), 1)
```

监听端口从 9999 改 9998 (adb reverse UsbFfs mode 在 Windows 下有 bug, 改用
RNDIS 直连手机 IP 10.239.217.199:9998)。

## 联调遇到的关键 Bug: EGL 跨线程静默失败

3.2.0.3f 第一次部署后, PC 端 `phonecam.py --connect 10.239.217.199:9998 --preview`
连上, 30s 后 "timed out" 断开重连, **收不到任何 NALU**。

### 排查过程

1. ✅ ADB ss -tnp 显示 9998 端口 ESTAB (PC↔Phone)
2. ✅ MainActivity listener 日志: `sActive=true egl=true enc=true` 持续输出
3. ✅ StreamingService 日志: TCP server up + H264Encoder started
4. ❌ H264Encoder 后台 output loop 一直 `INFO_TRY_AGAIN_LATER`, 从未出 NALU
5. ❌ EglRenderer.drawYuv 没有抛任何异常

### 根因

EGL context 是 **thread-local** 的:
- EglRenderer 在 StreamingService 启的 `Streaming-Service-Thread` 构造
  (initEgl 包含 eglMakeCurrent, 绑 worker thread)
- MainActivity listener 在 `imageReaderHandler` 线程调 `r.drawYuv(yuv, w, h)`
  → EGL call 在错误的线程 → **EGL 静默失败** (uploadTexture / glDrawArrays /
  eglSwapBuffers 都不抛异常, 也不渲染到 Surface)
- MediaCodec 收不到 input → dequeueOutputBuffer 永远 TRY_AGAIN_LATER

### 修复

创建专属单线程 executor `Streaming-EGL-Thread`, 把 EglRenderer 构造、drawYuv、
encodeFrame 全部跑在这个线程上:

```kotlin
// 在 Service worker thread 内:
val exec = Executors.newSingleThreadExecutor { r -> Thread(r, "Streaming-EGL-Thread") }
sEglExecutor = exec

// EglRenderer 在 EGL owner thread 构造 (latch 同步等)
val rendererLatch = CountDownLatch(1)
exec.execute {
    val r = EglRenderer(inputSurface)
    rendererHolder[0] = r
    rendererLatch.countDown()
}
rendererLatch.await(5, TimeUnit.SECONDS)
sEglRenderer = rendererHolder[0]
```

```kotlin
// MainActivity listener 调这个, 内部把任务投到 EGL owner thread
fun submitFrame(yuv: ByteArray, w: Int, h: Int) {
    val exec = sEglExecutor
    val renderer = sEglRenderer
    val encoder = sH264Encoder
    if (exec == null || renderer == null || encoder == null || !sActive) return
    exec.execute {
        try {
            renderer.drawYuv(yuv, w, h)
            encoder.encodeFrame(yuv)
        } catch (e: Exception) {
            Log.e(TAG, "EGL/encoder 异常", e)
        }
    }
}
```

## 经验教训

1. **EGL / OpenGL 是有线程亲和性的**, EGL context 绑在创建它的线程。
   MediaCodec Surface 路径必须保证: EglRenderer 构造、drawYuv、eglSwapBuffers
   都在同一线程。
2. **EGL 静默失败很危险**: 跨线程调 GLES/EGL API 不抛异常, 只返回 error code。
   必须在每步加 `GLES20.glGetError()` 检查 (后续批次补)。
3. **Oplus Hans 冻结**: ColorOS 14 上非前台应用的子线程会被冻结, 必须用
   前台 Service (startForeground) 保住线程。
4. **adb reverse UsbFfs 模式在 Windows 上有 bug**, 改用 RNDIS 直连手机 IP。
5. **adb input tap 触发的可能是长按**, 推流按钮初始文字要正确 + 用
   BroadcastReceiver 作为 ADB 入口。
