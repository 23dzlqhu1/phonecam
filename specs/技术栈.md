# PhoneCam 技术选型

> 🔧 **本文档作用**：明确每个模块用**什么库/什么语言**实现。
> 选型原则：**最成熟、最稳定、最容易上手**，而不是最热门。

---

## 1. 选型原则

| 原则 | 解释 |
|------|------|
| 🎯 **MVP 优先** | 先用熟悉、稳定的技术跑通链路，**不为未来 5% 的需求提前优化** |
| 👶 **新手友好** | 用户零基础，优先选文档多、社区活跃、调试简单的方案 |
| 🔌 **可替换** | 关键模块（编解码、虚拟摄像头）封装成接口，未来可换实现 |
| 🛠️ **复用现有** | `phone/` 已有 Flutter 工程、`desktop/` 已有 Python 框架，不全推翻 |

---

## 2. 总览

| 端 | 语言 | 核心框架 | 说明 |
|----|------|---------|------|
| 📱 手机 | Dart | Flutter 3.x | 跨平台、生态成熟、有 camera/shelf 插件 |

## 3. 手机端（Android）选型

### 3.1 必备库

| 模块 | 库 | 版本 | 为什么选它 | 替代方案 |
|------|-----|------|-----------|---------|
| 框架 | Flutter | 3.x（已用）| 已是项目现状 | React Native（不推荐，相机 API 弱）|
| 摄像头 | `camera` | ^0.11.0+2 | Flutter 官方插件 | camera2 原生（复杂）|
| HTTP/WS 服务 | `shelf` | ^1.4.2 | Dart 官方 HTTP 库，轻量 | aqueduct（重）|
| WebSocket | `web_socket_channel` | ^0.4.0 | 与 shelf 配套 | 直接 dart:io WebSocket |
| mDNS 发现 | `multicast_dns` | ^0.3.2 | 纯 Dart 实现 | 手动 UDP 广播 |
| 唤醒锁 | `wakelock_plus` | ^1.2.8 | 防止手机息屏断流 | - |
| **H.264 硬编码** | Android `MediaCodec`（Kotlin）| 系统 API | 硬编码，CPU 占用 < 5% | 软件 x264（CPU 爆炸）|

### 3.2 Kotlin 原生层

- **位置**：`phone/android/app/src/main/kotlin/com/phonecam/phone/`
- **已存在**：`H264EncoderPlugin.kt`（H.264 硬编码插件）
- **未来要加**：USB 反向网络通信（`adb reverse` 自动建立）

### 3.3 不选用的技术

- ❌ **React Native / Expo**：相机 API 弱，性能差
- ❌ **Native Android (Kotlin/Java) 全写**：开发速度慢，UI 难做
- ❌ **H.265/HEVC**：兼容性差，硬编码支持的手机比 H.264 少
- ❌ **WebRTC**：自研协议是我们的差异化，不引入现成方案

## 4. 电脑端（Windows）选型

### 4.1 必备库

| 模块 | 库 | 版本 | 为什么选它 | 替代方案 |
|------|-----|------|-----------|---------|
| 语言 | Python | 3.10+ | 项目现状、生态丰富 | C++（开发慢）、Rust（学习曲线陡）|
| H.264 解码 | `av` (PyAV) | >=12.0.0 | FFmpeg 绑定，支持硬解 (`-c:v h264_d3d11va`)| opencv-python（封装 VideoCapture，慢）|
| 视频帧处理 | `opencv-python` | >=4.8.0 | 项目现状，cv2 简单直接 | PIL（功能少）|
| 数值计算 | `numpy` | >=1.24.0 | 帧转换必备 | - |
| 图像处理 | `Pillow` | >=10.0.0 | 偶尔需要 | - |
| **虚拟摄像头** | `pyvirtualcam` | >=0.4.0 | **免驱动的关键**，自动调用 OBS Virtual Camera | 自写 DirectShow 驱动（地狱难度）|
| 异步 I/O | `asyncio` + `aiohttp` | 标准库 | TCP 接收、HTTP 发现 | threading（更难调试）|
| mDNS 发现 | `zeroconf` | latest | mDNS 标准库 | 手动 UDP |
| WebSocket 客户端 | `websocket-client` | >=1.6.0 | 简单可靠 | aiohttp 的 WS |

### 4.2 可选库（后期按需加）

| 模块 | 库 | 何时用 |
|------|-----|-------|
| GUI | `tkinter`（标准库）| MVP-3 之后做界面 |
| 系统托盘 | `pystray` | MVP-4 后台运行时 |
| 音频重放 | `soundcard` / `pyaudio` + `VB-Cable` | MVP-4 加音频时 |
| 打包 | `pyinstaller` | MVP-4 打 EXE |

### 4.3 不选用的技术

- ❌ **C++ / Rust 重写**：MVP 阶段性能不是瓶颈，PyAV + pyvirtualcam 已能跑 1080p60
- ❌ **OpenCV 的 cv2.VideoCapture**：解码 H.264 慢且无法用硬解
- ❌ **GStreamer**：学习曲线陡，PyAV 够用
- ❌ **FFmpeg 命令行调用**：进程开销大，不适合实时流

## 5. 协议（PCP）选型

### 5.1 传输层

| 方案 | 选 / 不选 | 理由 |
|------|----------|------|
| **TCP** | ✅ 选 | USB/局域网稳定，**先求稳再求快**。WiFi 弱信号下 UDP 丢包反而更卡 |
| UDP | ❌ 不选 | 1080p60 局域网丢包率 < 0.1%，TCP 体验更好 |
| QUIC | ❌ 不选 | 太复杂，依赖未广泛内置 |
| KCP | ❌ 不选 | 现成库少，需要自己实现可靠 UDP |

### 5.2 协议层（自研）

| 设计点 | 方案 |
|--------|------|
| 格式 | 二进制（紧凑，比 JSON 节省 30% 带宽）|
| 帧头 | 12-16 字节：`[4B seq][4B pts][2B flags][2B channel]` |
| 多路复用 | **单连接多通道**：video / audio / control |
| 控制信令 | **JSON over channel**（少量、易调试）|
| 媒体流 | **二进制帧**（大量、性能优先）|
| 错误恢复 | 关键帧请求 / 序列号丢帧检测 |

### 5.3 协议栈示意

```
┌────────────────────────────────────────┐
│  应用数据：H.264 视频 / AAC 音频 / 控制 JSON │
├────────────────────────────────────────┤
│  帧封装：seq / pts / flags / channel   │  ← 12-16 字节头
├────────────────────────────────────────┤
│  通道层：0x01=video  0x02=audio  0x03=ctrl│
├────────────────────────────────────────┤
│  TCP socket                             │
└────────────────────────────────────────┘
```

### 5.4 不选用的协议

- ❌ **MJPEG/HTTP**：1080p60 带宽 ~100Mbps，撑不住
- ❌ **RTSP/RTP**：标准但实现复杂，Iriun 不用
- ❌ **WebRTC**：现成方案，不能体现"自研"价值
- ❌ **SRT**：直播协议，低延迟但复杂

## 8. 关键技术风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| **Windows 虚拟摄像头驱动缺失** | 用户机器没装 OBS | pyvirtualcam 自动检测 + 友好提示 |
| **手机没有 H.264 硬编码** | 低端手机回退软编 | 启动时检测能力，自动降级 |
| **TCP 在 WiFi 弱信号下延迟高** | 用户体验差 | MVP 阶段走 USB；WiFi 阶段加带宽检测 |
| **PyAV 解码 CPU 高** | 占用过高 | 用 `h264_d3d11va` 硬解（Windows）|
| **USB 调试模式首次开启麻烦** | 新手卡住 | 文档 + GUI 引导 |
