# PhoneCam 技术选型

> 🔧 **本文档作用**：明确每个模块用**什么库/什么语言**实现。
> 选型原则：**最成熟、最稳定、最容易上手**，而不是最热门。

---

## 1. 选型原则

| 原则 | 解释 |
|------|------|
| 🎯 **MVP 优先** | 先用熟悉、稳定的技术跑通链路，**不为未来 5% 的需求提前优化** |
| 👶 **新手友好** | 用户零基础，优先选文档多、社区活跃、调试简单的方案 |
| 🔌 **可替换** | 关键模块（编解码、虚拟摄像头）封装成接口，未来可换实现 |
| 🛠️ **复用现有** | `phone/` 已有 Flutter 工程、`desktop/` 已有 Python 框架，不全推翻 |

---

## 2. 总览

| 端 | 语言 | 核心框架 | 说明 |
|----|------|---------|------|
| 📱 手机 | Kotlin | Android SDK + Camera2 + MediaCodec | MVP-2 起从 Flutter 切到 Kotlin 原生（ADR-006），链路最短、性能最优、APK 体积小 |
| 💻 电脑 | Python | Python 3.10+ | 快速开发、库丰富 |
| 🌐 协议 | 自研 | PCP（PhoneCam Protocol）| TCP 之上的二进制协议 |

## 3. 手机端（Android）选型

> ⚠️ **2026-06-08 路线重置（ADR-006）**：MVP-2 起从 Flutter 切到 **Kotlin 原生**（`phone_native/`，包名 `com.phonecam.nativeapp`）。旧 `phone/` Flutter 工程冻结作 legacy，**不直接动**。详见 `.ai/decisions.md` ADR-006。

### 3.1 选型原则

| 原则 | 解释 |
|------|------|
| 🎯 **链路最短** | Camera2 → MediaCodec → Socket，**3 跳同语言同进程** |
| ⚡ **性能优先** | 避免 Dart↔Kotlin 跨层数据拷贝 |
| 📦 **APK 体积** | Kotlin 原生 2-5 MB（vs Flutter 15-25 MB），工具 App "下载即用" 体验 |
| 🛠️ **调试直观** | logcat / Profiler / 栈跟踪全是 Android 原生工具链 |
| 📋 **UI 够用即可** | MVP-2 阶段只做 TextView + Button，漂亮 UI 留 MVP-4 |

### 3.2 必备库

| 模块 | 库 | 版本 | 为什么选它 | 替代方案 |
|------|-----|------|-----------|---------|
| 语言 | Kotlin | 1.9+ | Android 官方推荐、协程友好 | Java（啰嗦）|
| 摄像头 | Camera2 API | 系统 API | 直接控制预览 / YUV 回调 | CameraX（封装层，多一跳）|
| H.264 硬编码 | `MediaCodec` | 系统 API | 硬编码，CPU 占用 < 5% | 软件 x264（CPU 爆炸）|
| TCP 服务 | `java.net.ServerSocket` | JDK 标准库 | 简单直接，零依赖 | OkHttp（重）|
| 协程 | `kotlinx.coroutines` | 1.7+ | 摄像头回调 / TCP 异步 | Thread + Handler（啰嗦）|
| 视图绑定 | ViewBinding | Android Studio 默认 | 类型安全，零反射 | findViewById（手动）|
| **JSON**（如需要）| `org.json` | 系统自带 | 简单 | Gson / Moshi（MVP-2 暂时不用）|

### 3.3 包结构（`phone_native/app/src/main/java/com/phonecam/nativeapp/`）

| 文件 | 作用 |
|------|------|
| `MainActivity.kt` | 极简 UI：开始 / 停止 Button + 状态 TextView |
| `CameraController.kt` | Camera2 打开后置摄像头，YUV 回调到 H264Encoder |
| `H264Encoder.kt` | MediaCodec 编码 H.264 NALU |
| `PcpPacketWriter.kt` | 24 字节 PCP 头打包（与 `desktop/receiver.py` 协议一致）|
| `TcpStreamServer.kt` | ServerSocket 监听 0.0.0.0:9999，发送 PCP 包 |

### 3.4 复用旧 `phone/` 经验

- ✅ Gradle 阿里云镜像配置（`settings.gradle.kts` + `build.gradle.kts`）
- ✅ Gradle daemon 防火墙解决方案（`gradle.properties` + netsh advfirewall）
- ✅ `H264EncoderPlugin.kt` 编码逻辑（**仅参考**，新版本不走 MethodChannel）
- ❌ 不复用 Flutter UI 代码、camera 插件、shelf、web_socket_channel

### 3.5 不选用的技术

- ❌ **Flutter / Dart**：跨层复杂，APK 大，调试工具链多一套（详见 ADR-006）
- ❌ **React Native / Expo**：相机 API 弱，性能差
- ❌ **CameraX**（暂时不用）：封装层多一跳，Camera2 控制更直接
- ❌ **H.265/HEVC**：兼容性差，硬编码支持的手机比 H.264 少
- ❌ **WebRTC**：自研协议是差异化，不引入现成方案
- ❌ **ffmpeg-android / libx264**：背离"硬编码"选型，APK 体积爆炸
- ❌ **iOS / Swift**（参考 ADR-004）：MVP 阶段不做跨平台
- ❌ **漂亮 UI / Material 3 / 动画**（MVP-2 暂不需要）：MVP-4 产品化再做

## 4. 电脑端（Windows）选型

### 4.1 必备库

| 模块 | 库 | 版本 | 为什么选它 | 替代方案 |
|------|-----|------|-----------|---------|
| 语言 | Python | 3.10+ | 项目现状、生态丰富 | C++（开发慢）、Rust（学习曲线陡）|
| H.264 解码 | `av` (PyAV) | >=12.0.0 | FFmpeg 绑定，支持硬解 (`-c:v h264_d3d11va`)| opencv-python（封装 VideoCapture，慢）|
| 视频帧处理 | `opencv-python` | >=4.8.0 | 项目现状，cv2 简单直接 | PIL（功能少）|
| 数值计算 | `numpy` | >=1.24.0 | 帧转换必备 | - |
| 图像处理 | `Pillow` | >=10.0.0 | 偶尔需要 | - |
| **虚拟摄像头** | `pyvirtualcam` | >=0.4.0 | **免驱动的关键**，自动调用 OBS Virtual Camera | 自写 DirectShow 驱动（地狱难度）|
| 异步 I/O | `asyncio` + `aiohttp` | 标准库 | TCP 接收、HTTP 发现 | threading（更难调试）|
| mDNS 发现 | `zeroconf` | latest | mDNS 标准库 | 手动 UDP |
| WebSocket 客户端 | `websocket-client` | >=1.6.0 | 简单可靠 | aiohttp 的 WS |

### 4.2 可选库（后期按需加）

| 模块 | 库 | 何时用 |
|------|-----|-------|
| GUI | `tkinter`（标准库）| MVP-3 之后做界面 |
| 系统托盘 | `pystray` | MVP-4 后台运行时 |
| 音频重放 | `soundcard` / `pyaudio` + `VB-Cable` | MVP-4 加音频时 |
| 打包 | `pyinstaller` | MVP-4 打 EXE |

### 4.3 不选用的技术

- ❌ **C++ / Rust 重写**：MVP 阶段性能不是瓶颈，PyAV + pyvirtualcam 已能跑 1080p60
- ❌ **OpenCV 的 cv2.VideoCapture**：解码 H.264 慢且无法用硬解
- ❌ **GStreamer**：学习曲线陡，PyAV 够用
- ❌ **FFmpeg 命令行调用**：进程开销大，不适合实时流

## 5. 协议（PCP）选型

### 5.1 传输层

| 方案 | 选 / 不选 | 理由 |
|------|----------|------|
| **TCP** | ✅ 选 | USB/局域网稳定，**先求稳再求快**。WiFi 弱信号下 UDP 丢包反而更卡 |
| UDP | ❌ 不选 | 1080p60 局域网丢包率 < 0.1%，TCP 体验更好 |
| QUIC | ❌ 不选 | 太复杂，依赖未广泛内置 |
| KCP | ❌ 不选 | 现成库少，需要自己实现可靠 UDP |

### 5.2 协议层（自研）

| 设计点 | 方案 |
|--------|------|
| 格式 | 二进制（紧凑，比 JSON 节省 30% 带宽）|
| 帧头 | 12-16 字节：`[4B seq][4B pts][2B flags][2B channel]` |
| 多路复用 | **单连接多通道**：video / audio / control |
| 控制信令 | **JSON over channel**（少量、易调试）|
| 媒体流 | **二进制帧**（大量、性能优先）|
| 错误恢复 | 关键帧请求 / 序列号丢帧检测 |

### 5.3 协议栈示意

```
┌────────────────────────────────────────┐
│  应用数据：H.264 视频 / AAC 音频 / 控制 JSON │
├────────────────────────────────────────┤
│  帧封装：seq / pts / flags / channel   │  ← 12-16 字节头
├────────────────────────────────────────┤
│  通道层：0x01=video  0x02=audio  0x03=ctrl│
├────────────────────────────────────────┤
│  TCP socket                             │
└────────────────────────────────────────┘
```

### 5.4 不选用的协议

- ❌ **MJPEG/HTTP**：1080p60 带宽 ~100Mbps，撑不住
- ❌ **RTSP/RTP**：标准但实现复杂，Iriun 不用
- ❌ **WebRTC**：现成方案，不能体现"自研"价值
- ❌ **SRT**：直播协议，低延迟但复杂

## 8. 关键技术风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| **Windows 虚拟摄像头驱动缺失** | 用户机器没装 OBS | pyvirtualcam 自动检测 + 友好提示 |
| **手机没有 H.264 硬编码** | 低端手机回退软编 | 启动时检测能力，自动降级 |
| **TCP 在 WiFi 弱信号下延迟高** | 用户体验差 | MVP 阶段走 USB；WiFi 阶段加带宽检测 |
| **PyAV 解码 CPU 高** | 占用过高 | 用 `h264_d3d11va` 硬解（Windows）|
| **USB 调试模式首次开启麻烦** | 新手卡住 | 文档 + GUI 引导 |
